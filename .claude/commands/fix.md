# Fix

არგუმენტები (არასავალდებულო): $ARGUMENTS — finding-ების ID-ები (მაგ. `A-001 A-003`).

## ნაბიჯები
1. `AUDIT.md` არ არსებობს → მითხარი, რომ ჯერ `/audit` გავუშვა, და გაჩერდი.
2. `git status`: დაუკომიტებელი ცვლილებები → მითხარი და გაჩერდი (შეიძლება ჩემი იყოს).
3. თუ `team/` ან `fix/` ბრენჩზე არ ხარ → `git switch -c fix/<მოკლე-სახელი>`.
4. **არჩევა:** ჩემ მიერ მითითებული ID-ები; თუ არ მიმითითებია — ყველა დადასტურებული critical და should-fix, status: open. შესამოწმებელი და nit — მხოლოდ თუ სახელით მივუთითე.
5. გასწორება, რომელიც არქიტექტურას, API Contract-ს, ბაზის სქემას ან `PROJECT.md`-ის მოთხოვნებს ცვლის → **არ გაასწორო**; მონიშნე `needs decision` და ახსენი.
6. **თითო finding** (ერთი გადაცემა = ერთი finding; ერთ ფაილზე ორი აგენტი ერთდროულად არასდროს):
   - owner დეველოპერს მიეცი: finding-ის სრული ტექსტი, files, „done when" = პრობლემა აღარ მეორდება + ტესტი, რომელიც ძველ კოდზე ვარდება
   - report-ის შემოწმება `/auto`-ს ფაზა 2-ის მე-3 პუნქტის წესით (lint/typecheck/tests, `git diff --stat` report-თან შედარება)
   - ორჯერ `failed` → `blocked` მიზეზით, გადადი შემდეგზე
   - commit: `fix(A-00X): <title>`
7. **მიზნობრივი გადამოწმება:** reviewer, რომელმაც პრობლემა იპოვა, ამოწმებს მხოლოდ შეცვლილ ფაილებს.
8. `AUDIT.md`-ში სტატუსი: `fixed (verified)` — მხოლოდ თუ ტესტი ან ბრძანება ამტკიცებს; `fixed (reviewed)` — მხოლოდ კოდის კითხვით; `blocked`; `needs decision`. commit.
9. **საბოლოო:** `tester` — სრული შემოწმებები, შედარება აუდიტის baseline-თან (ტესტების რაოდენობის ჩათვლით).

## Report (ქართულად)
თითო finding: შედეგი და მტკიცებულება; საბოლოო შემოწმებები vs baseline; Unverified და როგორ შევამოწმო; needs decision; ბრენჩი და merge-ის ბრძანებები.
